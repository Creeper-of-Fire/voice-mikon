# qwen3-voice

基于本地 [Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) 的全局语音输入工具。

按一次全局热键开始说话,再按一次,识别出的文字直接粘贴到当前光标位置 —— 类似手机输入法,但在 Windows 上跑,音频完全不出本机。

---

> **许可证:AGPL-3.0-or-later**。录音胶囊的样式与波形算法移植自
> [OpenType](https://github.com/ct-jyjntc/opentype-public)(同为 AGPL-3.0),
> 见 [`LICENSE`](LICENSE)。

## 特点

- **录音胶囊悬浮窗**:按热键后弹出一颗胶囊 —— 上方是实时识别文字,
  下方是真实电平驱动的波形条和计时。识别完停留片刻自动隐藏,全程不抢焦点
- **胶囊位置三档**:默认**跟着输入光标**出现(像输入法候选框,贴着字不挡字),
  也可以改成固定底部,或者自己拖一个位置记住下来
- **常驻悬浮球**(可选,默认关):屏幕上常驻一颗小球,点它**原地展开成胶囊**
  开始说话,说完收回成球;拖球能挪位置,松手就记住。
  那颗球**就是这颗胶囊收窄成的圆** —— 一样大,展开是同一块东西在长开
- **预览可以关掉**:不想要实时预览文字条时,面板上一把开关 ——
  胶囊只剩波形、计时和按钮,一个字都不挡屏幕
- **真实电平反馈**:波形条由**真实音量数据**驱动,新条从右进旧条从左出,
  跟着声音流动。高度用非线性映射,小声也看得见;
  安静时就是安静的,不做假的抖动动画
- **随时可以反悔**:胶囊左边一颗 ✕,点了就丢弃这一轮 —— 不识别、不注入,
  一个字都不会贴出去
- **轻量配置面板**:面板只管状态、切换模型、切换主题、切换胶囊位置、
  开关预览文字、退出,默认不常驻(托盘打开),需要时再点出来
- **三档主题**:面板上一行「自动 / 白天 / 黑夜」,面板和胶囊**一起换** ——
  「自动」跟随 Windows 的应用模式,「白天」「黑夜」强制固定
- **全局热键**:`Ctrl+Alt+Space` 随处可用,系统级注册,不需要管理员权限
- **完全本地**:模型跑在本机 GPU,音频不出本机,断网可用
- **模型常驻**:0.6B / 1.7B 随时切换,切换后热键零等待
- **也能走网络**:不想在本机跑模型时,面板上一键切到阿里云百炼网络接口
  (音频会出本机)。两种后端**互斥** —— 切走后本地模型从显存里卸掉,
  切回来再重新加载
- **不吞剪贴板**:借用了剪贴板就一定还回去;但你在这期间复制了新内容,
  我们的恢复会主动让位,绝不覆盖你刚复制的东西
- **不替模型做判断**:录到多少就送多少,识别得到就是结果、识别不到就提示
  「没听清」。**没有**静音门、时长门这类本地预判 —— 你的话该不该听,
  由模型说,不由阈值说
- **焦点保护**:转写这 1 秒里你切了窗口,文字仍然贴回原来的窗口

## 安装

需要 Python 3.12+ 和一块 NVIDIA 显卡(8GB 显存足够)。
面板基于 WebView2 渲染,Windows 10/11 一般都自带这个运行时,一般不用额外装。

```powershell
# 1. 建环境
uv venv --python 3.12 .venv

# 2. 装依赖
uv pip install --python .venv\Scripts\python.exe -e .

# 3. 下载模型权重(国内走 ModelScope 更快)
modelscope download --model Qwen/Qwen3-ASR-0.6B --local_dir D:\Dev\Environments\models\Qwen3-ASR-0.6B
modelscope download --model Qwen/Qwen3-ASR-1.7B --local_dir D:\Dev\Environments\models\Qwen3-ASR-1.7B
```

模型权重路径写在 `config.example.json` 的 `model_root` 里。

## 使用

```powershell
python -m qwen3_voice
```

启动后:

1. 托盘图标出现在右下角(灰=待机,黄=加载中,红=录音中)
2. 按 **Ctrl+Alt+Space**,胶囊贴着输入光标出现:
   上方是实时识别文字,下方是波形条和计时
3. 说话。再按一次热键(或点胶囊右边的 ✓)结束,文字自动出现在你原来
   光标所在的位置,胶囊定格一下「已输入」然后自动隐藏
4. 想放弃这一轮,点胶囊左边的 ✕ —— 不识别、不注入
5. 需要切模型、切主题、调胶囊位置或退出,点托盘图标打开面板
   (面板默认不常驻)

出错了(没听清、识别失败、注入失败)时,胶囊上的文字条
会变成红底并显示原因(深色主题下是暗红底,浅色主题下是浅红底),停 4.5 秒再自动隐藏。
注入失败是例外:文字条显示**识别原文**并停 12 秒,胶囊上多一个「复制」按钮,
错误文案会点明"文字已留在剪贴板" —— 没送达就不归还剪贴板是注入层的规矩,
按 Ctrl+V 立刻能贴出来,不会白说。

> 面板位置会被记住;胶囊默认跟着输入光标走(也可以改成固定底部,或自己
> 拖一个位置记住下来 —— 位置存的是相对工作区的偏移,换屏换缩放都不飞)。
> 面板上的「预览」开关可以把实时预览文字条整个关掉,此时胶囊里只剩
> 波形、计时和按钮。

### 常驻悬浮球(可选)

面板上打开「悬浮球」之后,屏幕上会常驻一颗小球:

- **点它** → 球原地展开成胶囊,开始录音;录完胶囊收回成球,继续常驻
- **拖它** → 挪位置,松手记住(**「自定义」档**;"跟随输入 / 固定底部"
  档的位置不归用户管,不能拖,见下文)
- **右键它** → 通用功能菜单(一个展示框,里面一排小圆圈,以后加新功能
  都往这里放)。现有两项:**设置**(打开面板)和**退出**(走托盘同一条
  清理路径,不是简单 kill)

球是**录音红**的(和胶囊的 ✓ 按钮同一个红):它常驻在屏幕角落,
必须一眼就能找到 —— 深底浅描边的球太低调,人会"忘了它在"然后去按热键。
图标做极轻的呼吸,示意"随时能说话"。

**启动 / 重启后模型还在加载的几秒钟**,球上的图标会换成转圈 ——
提示"还不能录";这时点球会被拒绝,球上方冒一句"模型加载中…",
就绪后自动恢复成麦克风。

那颗球**不是另一个元素** —— 它**就是这颗胶囊收窄成的正圆**(40×40,
和胶囊的高度一样大)。展开时是同一块胶囊横向长开,收起来是同一块收窄:
所以两者永远严丝合缝,不会出现"球和胶囊对不上"的接缝(见下面的坑)。

#### 球的位置:跟随输入 / 记住位置 / 常驻

面板上「球位置」这一行有三档,默认「跟随输入」:

| 档位 | 球在哪 | 什么时候出现 | 能不能拖 |
|---|---|---|---|
| **跟随输入** | 光标旁边(像输入法候选框) | 光标**真的落在输入框里**时;离开就消失 | **不能** |
| **记住位置** | 拖出来的地方,位置被记住(换屏按显示器名还原) | 光标**真的落在输入框里**时;离开就消失 | 能,拖完就记住 |
| **常驻** | 同一份记住的位置 | **一直显示**(球就是录音入口,随时在) | 能,拖完就记住 |

「记住位置」和「常驻」**共用同一份记住的位置** —— 两档的差别只在
显隐:一个要光标聚焦才出现,一个一直在。这和胶囊的「位置」三档
(跟随输入/固定底部/自定义)是**两套独立设计**:球的档里没有"固定底部",
却有"记住位置"这种胶囊没有的东西;档位名相同也不代表含义相同。
两边各自演化,面板上又因「位置 / 球位置」互斥显示(见上),不会混淆。

「光标落在输入框里」的判定是**真光标**:只认 UI Automation /
传统控件 caret,外加一级**空输入框兜底**(焦点在可编辑框里但一个字符
都没有,UIA 扩不出字符矩形 —— 退化成输入框的左下角)。
读不到光标就**不显示球**,不会退化成"跟着鼠标走"或"躲到窗口角落" ——
一个不知道自己在哪的球比没有球更糟。

跟随档的球**完全不响应拖动**(和胶囊在跟随档下不响应拖动是
一个道理):位置归光标,拖了也会被拉回去。与其让用户拖了个寂寞,
不如直接不响应,光标形状也不给"能拖"的假象。点它开始录音照常;
「记住位置 / 常驻」两档照常可拖、拖完记住。

**切档为什么曾经"没反应"(修过的坑)**:follow 和「记住位置」靠一个
250ms 的轮询线程维持显隐,线程里"问一次光标位置"(UIA)要几十到几百
毫秒 —— 切档的瞬间旧线程可能正攥着一个刚问到的位置,醒来把球又挪回
光标处或者把球藏掉,新档位的摆位就被盖掉了。修法是给线程发**代数**
(epoch):起/停线程都让计数 +1,线程动窗口前发现代数变了就立刻收手;
切档侧先停线程(等到它真退出)再摆位。

两点和直觉不太一样,说明一下:

1. **常驻模式下,胶囊的位置由球决定**,不再"跟着输入光标"跑 ——
   常驻的东西不该乱跑。想换位置,拖球就行。
2. **球的上方要留得下展开后的胶囊**,所以球不能拖到屏幕最顶端 ——
   不然展开后文字条会出屏。

想关掉随时在面板上关,或者把配置里的 `floating_orb` 设成 `false`。

### 术语表(热词)

Qwen3-ASR 内置一个叫 **Context Biasing** 的能力:可以传任意文本
(API 上限 10000 token)把转写**偏向**特定术语 —— 公司名、产品代号、
医疗术语、法律行话、领域黑话都靠它校准。官方原话是「当音频模糊时,
模型会优先选这些词」。

配置里填词、逗号分隔即可:

```json
"hotwords": ["杀鲸乾坤道", "终极真身", "迦勒底"]
```

会拼成 `Vocabulary: 杀鲸乾坤道, 终极真身, 迦勒底.` 送进模型的 system role
(这个格式是官方 HF 版的写法,模型在 SFT 阶段就是用它训练上下文偏置的,
自己编一句提示效果会打折)。

**这是识别阶段的偏置,不是识别完再改写** —— 所以不会凭空猜错别字,
也不会改掉原意,和你不想要的「LLM 润色」是两回事。

#### 效果(实测)

同一段音频,专有名词 `Qwen3-ASR`:

| context | 识别结果 |
|---|---|
| 空 | `请帮我查一下服务器上那份叫做"Queen三ASR"的模型权重文件。` ❌ |
| `Vocabulary: Qwen3-ASR, Qwen3, ASR.` | `请帮我查一下服务器上那份叫做 Qwen3-ASR 的模型权重文件。` ✅ |

所以术语表值得认真维护。

#### 术语表管理器(打分器工作流)

术语表最难的是「哪些词值得收录」—— 这个判断不该由代码或 agent 代劳,
所以提供的是**打分器**而不是筛选器:全量候选公开给你,你来定夺。

```bash
python scripts/hotwords_manager.py scan     # 聊天记录 → 全量候选(带分数)
python scripts/hotwords_manager.py build    # 候选 + 你的编辑 → 最终词表
python scripts/hotwords_manager.py show     # 查看最终词表
```

三个文件,一条流水线(全部在 `data/` 下):

| 文件 | 谁写 | 作用 |
|---|---|---|
| `hotwords_candidates.tsv` | scan 产出 | **全量候选,零筛选**:分数/频次/类型/示例上下文 |
| `hotwords_user.tsv` | **你** | 手动编辑,永不被覆盖:`=` 强制收录 / `!` 拉黑 / `+N` 加分 |
| `hotwords.txt` | build 产出 | 最终词表,**每次识别时实时读取**(mtime 缓存),改完立即生效 |

scan 的中文部分用 **jieba 分词**(需要 `pip install jieba`),不是 n-gram ——
n-gram 会产生"我还/不知/道怎"这类跨词碎片,分词以词为单位,
"固有/歧义/采样率"都是完整词。试过把 Qwen tokenizer 词表喂给 jieba
做增强,负收益(专业术语在 BPE 里本来就是拆开的,词表里全是通用组合),放弃。

只取 `role == "user"` 的正文(用户手打的内容才是术语的真实形态),
拉丁 token 按「紧邻汉字(+15)/cmdlet 形态(-10)/文件名(-20)」等规则打分;
分数只是排序建议,**不替你做决定**。

你的编辑示例(`data/hotwords_user.tsv`,Tab 分隔):

```
玉藻前	=	老师
固有	+40	常用表达
Monte Carlo	!	太通用
```

**词条要克制** —— 词越多偏置越强,但也越容易把没说的话写出来。
build 默认取分数前 120(`--top` 可调),强制收录不受限。
优先收录「读音和写法差别大」的词(Queen/Qwen、三ASR/ASR),
拼写本来就对得上的(`API`、`PDF`)帮助不大。

仓库里有编辑文件模板:`hotwords_user.example.tsv`。

## 两种识别后端(本地 / 网络)

面板上多一行「后端」:本地模型 ↔ 阿里云百炼 DashScope 网络接口。
**两者互斥** —— 同一时刻只留一个,切走后旧的会被卸载。

| | 本地(默认) | 网络(DashScope) |
|---|---|---|
| 音频去哪 | 不出本机 | 发给阿里云百炼 |
| 断网 | 照常用 | 用不了(但能随时切回本地) |
| 热键延迟 | 零等待(模型常驻显存) | 多一次网络往返(几百毫秒 ~ 数秒) |
| 实时预览 | 有(边说边出字) | **没有**(见下) |
| 显存 | 常驻几 GB | 切过去后本地模型被卸载,不占显存 |
| API Key | 不需要 | 需要环境变量 `DASHSCOPE_API_KEY` |

### API Key 怎么配

**只从环境变量读,不进 `config.json`** —— 配置文件会被手工编辑、截图、分享。

```powershell
# 只对当前这个 PowerShell 窗口有效
$env:DASHSCOPE_API_KEY = "sk-..."

# 永久(写进用户环境变量,新开的终端都生效)
[Environment]::SetEnvironmentVariable("DASHSCOPE_API_KEY", "sk-...", "User")
```

没配 key 时切到网络会**明确报错**(「未配置 DASHSCOPE_API_KEY 环境变量」),
**不会静默回落到本地** —— 静默回落会让人以为自己在用网络。

### 网络模式没有实时预览

预览的价值是「边说边出字」,而兼容端点是**整段请求**:录完一次性发出去。
硬做逐句预览只能反复重发全量音频 —— 烧配额,而且延迟越滚越大。所以网络模式下:

- 预览文字条**整个不出现**(胶囊只剩波形 + 计时 + 按钮)
- 面板上「模型」「预览」两行置灰,并有一行说明文字 ——
  **行为差异写出来,不当黑盒**
- 切回本地后预览照旧(用户的预览开关偏好不会被改掉)

### 热词在网络模式怎么传

和本地一样是 **Context Biasing**,格式一模一样:
`Vocabulary: 杀鲸乾坤道, 终极真身.`

- 本地后端:交给 `qwen_asr` 的 `context` 参数
- 网络后端:放进 **system prompt**

两边效果可比,词表不用改(还是 config.json 的 `hotwords` + `data/hotwords.txt`)。

### 互斥切换对显存的影响

- **切到网络**:本地模型被 `del` 掉,并调 `torch.cuda.empty_cache()` ——
  显存**真的**还给系统(不然「切到网络省显存」就是空话)
- **切回本地**:重新加载模型,几秒(这期间热键不可用)
- 切换在**后台线程**里做,面板不卡
- **录音中 / 识别中不能切换**:会被拒绝并在面板上提示。
  这一轮的最终位引擎还握着旧后端的引用,中途换掉会出错或丢结果

| hotkey 线程 | RegisterHotKey + GetMessage | Win32 消息队列是线程局部的 |
| tray 线程 | pystray 消息循环 | pystray 自带循环 |
| model / mic 线程 | 后台初始化 | 不阻塞启动 |
| asr 线程 | 识别与注入 | 不阻塞 UI |

## 踩过的坑

**ctypes 句柄截断**
`GlobalLock` 不声明 `restype` 时,ctypes 默认按 `c_int` 处理返回值,64 位句柄被截断,
写剪贴板会写到非法地址,进程直接崩(0xC0000005)。所有 Win32 签名在 `win32/api.py` 里显式声明。

**蓝牙耳机采不到数据**
EDIFIER W800BT Plus 这类蓝牙耳机,在 WASAPI 共享模式下会被 Steam / 网易云占住音频端点。
设备声称支持某采样率,实际打开后只拿到零星数据。所以 `audio/devices.py` 会**实测**每个设备
(录 2 秒看能采到多少),而不是只看名字。

**必须用设备原生采样率采集,但不要自己降采样**
按 16 kHz 直接打开蓝牙设备,WASAPI 会悄悄降速,2 秒只采到 0.38 秒,录音被截断。
所以按**设备原生率**采集(本机实测 48 kHz)。但降采样**不要自己做** ——
把 `(原生音频, 原生采样率)` 直接交给 `qwen_asr`,它内部用 librosa 做高质量重采样
(与官方评测路径完全一致)。

自己用 `np.interp` 线性插值降采样有两个问题:
1. 没有抗混叠低通滤波,8~24 kHz 的成分会折叠回低频,叠在人声基频上
   (实测失真能量占比 98.71%,其中 88% 落在 0~4 kHz 语音主频带)
2. 单条短句上差异不明显,但长句会明显退化

**网络后端自己重采样,也不能用 `np.interp`**
本地后端把音频交给 `qwen_asr`,重采样由 librosa 内部完成(见上)。
网络后端没有 librosa 可靠地跟着走(只依赖 scipy + 标准库),所以重采样自己来 ——
但**照样不能用线性插值**:48 kHz 采到的 12 kHz 降到 16 kHz 会折回 4 kHz。
用的是 `scipy.signal.resample_poly`(多相滤波,带抗混叠低通)。
`tests/test_network_engine.py` 里有一条对照测试
(`test_linear_interpolation_would_fold_the_same_signal`)把这个坑钉住了。

**API Key 不能进配置文件**
网络后端的 key 只从环境变量 `DASHSCOPE_API_KEY` 读。
`config.json` 会被用户手工编辑、截图、分享 —— key 写进去就等于送出去。
缺 key 时**明确报错**,不静默回落到本地(那会让人以为在用网络)。

**int16 混音时别把整数当浮点缩放**
`sounddevice` 回调给的是 `(frames, channels)` 的 int16。`arr.mean(axis=1)` 会把
int16 提升成 float64,此时若再走「浮点音频 × 32768」那条分支,原始刻度
(比如 1000)会被当成 [-1,1] 浮点乘 32768 → 32768000 → 削波成 32767。
实测**46.5% 的样本变成满刻度**,音频被削成方波,模型看到的是严重失真的信号。
`audio/recorder.py:frames_to_int16` 里对 int16 单独走 `astype(np.int16)` 还原刻度。

**dtype 判断要在混音之前**
上面那个坑的通用形态 —— `mean` 会把 int16 提升成 float64,所以
**先记下原始 dtype,再混音,最后按原始刻度还原**。
`asr/engine.py:_to_float32` 里如果写成「先 mean 再判断是不是整数」,
判断就永远不成立,int16 会被当成已归一化的浮点,直接 clip 成 ±1(全幅方波)。

**传给 qwen_asr 的必须是浮点音频**
`qwen_asr` 内部用 librosa 重采样,而 librosa 只接受浮点 —— 传 int16 会报
`ParameterError: Audio data must be floating-point`。
所以 `asr/engine.py:_to_float32` 负责把 int16 转成 [-1,1] 的 float32。

**热键路径上不能做耗时操作**
早期版本在按热键时同步做 2 秒设备探测,导致用户按下的前 2 秒说的话全丢。
现在设备探测在后台预热,结果走缓存,热键路径零延迟。

**qwen_asr 的音频输入格式**
必须是 `(np.ndarray, sample_rate)` 元组或文件路径,传裸 ndarray 会报
`TypeError: Unsupported audio input type`。

**高分屏必须声明 DPI 感知**
本机 175% 缩放。声明之后,`GetDeviceCaps(GetDC(0), LOGPIXELSX)` 就**不可靠了** ——
进程是 Per-Monitor V2 感知时,这个值取决于调用线程的 DPI 上下文,不同线程拿到的
结果不一样(实测主线程 96、探测线程 168),拿它算位置会把窗口甩到屏幕外。
改用 `GetDpiForSystem()`(主显示器 DPI,与线程无关)和 `GetDpiForWindow(hwnd)`
(窗口所在显示器)。

**定位光标没有单一可靠的 API**
现代应用(Chrome / VSCode / Office / Electron)要走 UI Automation,
传统控件(记事本这类)走 `GetGUIThreadInfo` 的 `rcCaret`,再不行才退到
鼠标位置、前台窗口矩形。所以是**四级回退**,谁准用谁。UIA 那级要
`comtypes`(可选依赖 `pip install -e ".[uia]"`)—— 没装就自动降级,
功能少一档,但不该让整个跟随模式不可用。

UIA 上还有两个坑:一是**不能直接用 `GetCaretRange`** —— 那方法只在
`IUIAutomationTextPattern2` 上,而实测绝大多数应用只实现 v1,QI 到 v2
直接 `E_NOINTERFACE`;v1 上只能借"选区"反推(插入点 = 空选区,把它
扩到所在的字符就有矩形了)。二是 **`rcCaret` 的坐标基准不是屏幕坐标**
(MSDN 写错了,实测是焦点控件的相对坐标),不换算胶囊会跑到屏幕左上角。

**多显示器的位置要用 EnumDisplayMonitors,不能用 GetSystemMetrics**
`GetSystemMetrics` 只回答主屏的问题,副屏的坐标原点、缩放都可能是另一套。
而且工作区(任务栏之外的区域)和整块屏幕不是一回事 —— 按整块屏摆,
胶囊会被任务栏盖住底边。`win32/monitors.py` 用 `EnumDisplayMonitors`
逐块枚举,顺带拿每块屏的有效缩放(`GetDpiForMonitor`,与线程无关)。

**pywebview 给的初始窗口尺寸会被 WinForms 再缩一次**
请求 300x260 逻辑像素,实际客户区只有 286x224 —— 底部几个像素的内容被裁掉了。
根因是 WinForms 的 `AutoScaleMode.Dpi`。但 `window.resize()` 走的是另一条路径,
尺寸是准的(实测 `resize(300,320)` 得到的正好是 320 逻辑像素)。
所以面板的做法是:**显示后自己量一次 `document.body.scrollHeight`,再 resize 到刚好**,
而不是相信建窗时给的尺寸。

**canvas 的 flex-basis:auto 会被它自己的默认尺寸撑大**
`<canvas>` 没有 CSS 尺寸时,默认属性尺寸是 300x150。在 flex 容器里
`flex-basis: auto` 取的就是这个属性高度 —— 电平条卡片会被撑到 162px,
把结果卡片挤成 0 高度,文字直接看不见。
必须给 canvas 一个确定的 flex-basis(`flex: 1 1 44px`)。

**WebView2 的用户数据目录要显式指定**
WebView2 默认把 Cookies / 缓存 / LocalStorage 写到 `%LOCALAPPDATA%`,
那违反 portable 约定。而且只设 `WEBVIEW2_USER_DATA_FOLDER` 环境变量**不够** ——
pywebview 会在 `start()` 里显式设置 `UserDataFolder` 把它覆盖掉,
所以两个都要给:环境变量 + `webview.start(private_mode=False, storage_path=...)`。

**电平必须推绝对值**
电平条如果按「窗口内最大值」归一化,波形永远看起来是满的,
用户就没法从条的高低看出「我说话声音大不大」—— 那条电平条就只剩装饰作用了。
所以 Python 侧把 RMS 映射成 dBFS(下限 -70 dB,上限 0 dB)再推给前端,
前端不做任何窗口归一化。下限定在 -60 也不行:实测安静房间的底噪就有 -62 dBFS,
会被压成 0,电平条看着像死了。

**模型路径拼接别搞错**
`model_root / repo` 和 `model_root / model_tag` 是两个不同的路径。
写成前者会去找 `models\Qwen\Qwen3-ASR-0.6B`,找不到就退回联网下载,然后
在离线环境下报一长串 `MaxRetryError`。

**真实音频设备会让进程退出时崩 0xC0000005**
真设备的 PortAudio 清理有这个坑,排障脚本里也一样:能不打开真实设备
就不打开,要打开就在独立进程里做。

**电平条要加噪声门,否则安静时也像在响**
实测安静房间的底噪是 -62 dBFS,映射到 0..1 还有 0.11,超过当时的死区(0.04) ——
结果电平条一直显示 7px 高度,看着像一直在响。所以映射前先过一道噪声门
(用 `config.silence_rms`),低于门限直接判 0。加了之后实测:
安静房间录 3 秒,映射后全是 0.000;有人声时均值 0.42、最高 0.71。

**但那扇门是按当时的环境校准的,换个环境就不作数**
2026-11-07 实测本机底噪中位 **-52.6 dBFS**(p10 -53.8 / min -55.5),
比当初假设的 -62 dBFS 高了 9 dB —— `silence_rms=0.002`(-54 dBFS)直接被
底噪穿过去:底噪映射成 0.23~0.25,前端按高度映射画成 12~13px
(满格 20px 的 65%),安静时看着照样像在响。

修法是**动显示层的死区,不动后端那扇门**:后端门抬高等于用本地阈值
替用户决定这句话算不算数(轻声容易被误杀),显示层才是它该管的事。
前端死区 0.04 → 0.30(-49 dBFS):底噪落在下面画 2px 灰条,
轻声说话(-45 dBFS → 0.36)照常有反应。

**静音时也要诚实地显示**
录音中但没声音(电平 ≤ 0.30)时,显示 2px 的灰条并继续滚动,而不是冻住或隐藏 ——
"在录但没声"和"没在录"是两回事。反过来,**待机(根本没开始录音)时就不该显示
条形**,改成一行状态文字;显示会动的假动画是在骗人。

**点悬浮球开始录音时,前台也会被胶囊抢走**

WebView2 的内容窗口属于 `msedgewebview2.exe`,跨进程加不了 NOACTIVATE ——
鼠标点上去会激活整棵窗口树、抢走前台。点胶囊上的 ✓/✕ 靠 `_give_back_focus()`
兜着;点悬浮球开始录音是同一条路,后果更重:注入靠"粘贴到前台窗口",
前台要是成了胶囊,这一轮识别完的文字会贴到**胶囊自己**身上,而不是用户的
输入框 —— 功能级的致命 bug,不是观感问题。

**球和胶囊不一样大,展开瞬间会被切出一道白线**

窗口命中区靠 `SetWindowRgn` 裁:前端量出可见内容的矩形,Python 按它裁形状,
大片透明空白才不吃底下应用的点击。

早先悬浮球是**另一个 DOM 元素**,和胶囊各占一块,展开时球淡出、胶囊长出。
两者**尺寸不一致**(球 56px、胶囊只有 40px 高),展开那一瞬间,窗口按上报的
矩形一裁,球的上半截就被切掉一条 —— 看起来像"球冠上多了一道白线"。

现在的解法是把球**并进胶囊**:那颗球就是这颗胶囊收窄成的正圆(40×40),
前端只有一颗元素,展开是同一块矩形横向长开。

三条规矩一起上:

1. **球和胶囊必须一样大**(球径 = 胶囊高度 = 40px)。`placement.ORB_SIZE`
   和 CSS 里的 `height` / `max-width` 是一份约定写在两处,改一边忘了
   另一边就会复现那道白线 —— 动手前先看两边。
2. **形变不用 `transform`**。宽度靠 `max-width` 过渡(实际宽度 =
   min(fit-content, max-width),从 40px 长到内容宽度)。`transform` 会让
   "视觉形状"和"上报的矩形"错位 —— `getBoundingClientRect()` 把 transform
   一起算进去,按它裁窗口,描边两端就会被切掉(实测:上下边线在两端断着,
   中间完好,一眼像"渲染坏了")。
3. **形变期间要持续上报命中区**。宽度在 0.3s 里每帧都在变,只在头尾各报
   一次的话,中间那 0.3s 里窗口形状停在"球"那一小块,胶囊多出来的那部分
   点不到(会穿透到底下的应用)。所以形变期间每 50ms 报一次。

另外,量矩形一律用 `offsetLeft/offsetTop/offsetWidth/offsetHeight`
(**布局**尺寸,不受 transform 影响),不用 `getBoundingClientRect()`。
动效结束(`transitionend`,外加 520ms 的定时器兜底 —— `prefers-reduced-motion`
下 transition 是 `none`,压根不会触发 `transitionend`)再补报一次。

所以点球的路径是:**先把前台还给用户,再开始录音**。用户原先所在的窗口
由守卫线程动态跟踪(`_last_foreground`),不要靠猜。

顺带一条:鼠标点在 WebView2 的子窗口上会**抢走鼠标捕获**,所以拖动期间
守卫不能来回抢焦点(焦点跳来跳去会把拖动打断)—— 按下就先告诉 Python
"开始拖",松手再统一还一次。

**胶囊显示绝不能抢焦点**
抢了焦点,后面注入的文字就没有落点了 —— 光标会被抢到胶囊上,文字全丢。
pywebview 的 `window.show()` 内部会调 WinForms 的 `Activate()`,必然抢焦点。
所以胶囊显示一律走 Win32:先给 hwnd 加 `WS_EX_NOACTIVATE`,
再用 `ShowWindow(hwnd, SW_SHOWNOACTIVATE)`。

**pywebview 对透明窗口自带一个抢焦点的 hack**
winforms 后端的 `EdgeChrome.on_navigation_start` 里有一段:透明窗口在
页面**开始导航**时会 `form.Show()` + `form.Activate()`(源码注释写着
"no idea why this works")。后果是胶囊在**启动时**就自己冒出来,
还占住前台,用户的键盘输入全进了胶囊。
`WS_EX_NOACTIVATE` 拦不住它 —— `Activate()` 走的是 `SetForegroundWindow`,
那是程序显式激活,不是"用户点击"。

定点修法:在 `before_show` 事件里把 `window.transparent` 置 `False`。
这个时机唯一能同时满足两件事:BrowserForm 的构造函数**已经**按
`transparent=True` 设好了 WebView2 的 `DefaultBackgroundColor = Transparent`
(透明不受影响),而导航还没开始(那段 hack 因此不执行)。
`before_show` 是同步事件,没有竞态。

**透明窗口一旦被 resize,透明就失效**
pywebview 的透明窗口只要被 `SetWindowPos` 改过尺寸,WebView2 就会
用 Form 的背景色(`#F0F0F0`)把整块客户区填掉 —— 窗口外的区域从
"透出桌面"变成"一块灰底"。实测:resize 前透明、resize 后灰底。

色键(`WS_EX_LAYERED` + `LWA_COLORKEY`)对 WebView2 这个子窗口无效
(灰底是 WebView2 自己画的);resize 后再重设 `DefaultBackgroundColor`
又会被 CoreWebView2 的"只能从 UI 线程访问"挡下来。

所以胶囊窗口**固定尺寸**(512×260 逻辑像素 —— 请求值会被 WinForms
AutoScale 缩水,建窗时放大补偿),不做高度自适应 ——
内容用 CSS 贴着窗口底部排,文字条到 `max-height` 就自己内部滚动。
窗口空白区不属于命中区:前端把"文字条+胶囊"的矩形上报给 Python,
`SetWindowRgn` 把窗口裁成内容形状,空白处点击直接穿透到底下应用。

**透明窗口的背景要三层都透明**
窗口(html / body)少写一层 `background: transparent` 就会露出一块
不透明的底色 —— 根元素的背景会传播到 canvas,所以 `html` 这一层
不能省。

**还原焦点不许模拟按键**
把焦点还给用户原来的窗口,只能用 `AttachThreadInput` +
`SetForegroundWindow`。绝不能用 `keybd_event` / `SendInput` 之类
"模拟 Alt 键"的老套路 —— 那会往用户的输入流里插东西,正在打字的人
会打出多余的 Alt 组合。

**透明窗口上不能有 box-shadow / backdrop-filter**
它们在透明窗口上会渲染成一条灰带,非常难看。层次只靠"深底 + 半透明描边"。

**波形区不能用「一块底色盖住」来做渐隐**
滚动电平条的左边缘要渐隐(条子滑出去时不能被硬切一刀)。
早先的做法是盖一块 10px 宽的渐变块,颜色用 `var(--deep)` ——
看着等价,其实是错的:
1. 盖子的颜色是**静态**的,而球展开成胶囊时底色正从红褪成深/白,
   红底上就凭空多出一块不属于它的渐变块 —— 真机观感:丑陋的残影;
2. 浅色主题下盖子是白的,压在红底上尤其刺眼。

正确做法是 `mask-image`:条子**自己**在那个位置变透明,跟底色无关。
另外 `mask-size` / `mask-repeat` 必须写死(`100% 100%` / `no-repeat`)——
渐变图没有固有尺寸,默认的 auto/repeat 会把它当成 10px 宽的小图平铺,
波形区于是变成一条条忽明忽暗的条纹,条子几乎看不见。

**跟随档下就不该有拖动**
光标跟着走的东西,拖了也会被下一轮轮询拉回去。与其让用户拖了个寂寞,
不如直接不响应 —— 前端连 mousemove 都不挂,光标形状也不给"能拖"的假象。
点击(开始录音)照常保留,用"按下到松开的位移"区分"点了一下"和"按着划走"。

**切档要先用线程代数(epoch)停掉旧轮询,再摆位**
球的 follow/bottom 档靠轮询线程(250ms)维持,线程里"问一次光标位置"
(UIA)要几十到几百毫秒 —— 切档事件到达时旧线程可能正攥着一个刚问到的
位置,醒来把球又挪回光标处、或者把球藏掉,新档位的摆位就被盖掉了。
用户看到的就是"切了档没反应"。修法:起/停线程都让代数 +1,线程在
**动窗口之前**发现代数变了就立刻收手;切档侧先 `_stop_follow_thread()`
(join 到线程真退出)再做本次摆位。光改配置不管线程,竞态一定复现。

**热键注销必须投到热键线程自己的队列**
`RegisterHotKey(NULL, ...)` 注册的热键是**线程局部**的,`UnregisterHotKey`
也必须由**注册它的那个线程**调用 —— 别的线程调会失败。所以注销只能写在
线程自己的 `finally` 里;而要让线程退出 `GetMessage` 循环,得往**那个线程**
的消息队列投 WM_QUIT:`PostThreadMessageW(thread_id, WM_QUIT, 0, 0)`。

用 `PostQuitMessage` 是错的 —— 它投给的是**调用线程自己**的队列,热键线程
永远收不到,`GetMessage` 一直阻塞,`finally` 里的注销永远不执行。症状:
退出时白等满 timeout(好几秒)、快捷键一直被占着、"退出后马上重启"直接
注册失败。另外 `user32.dll` **没有**裸的 `PostThreadMessage` 导出,只有
A/W 后缀版(写成无后缀的会在 import 时就 AttributeError)。

**退出流程里热键要第一个停**
热键是**全局**资源:本进程不注销,别的实例就注册不上同一个组合键。
所以它不能排在模型卸载(好几秒)后面 —— 挂在 `controller.shutdown()` 的
最前面,三条退出路径(托盘菜单 / 面板按钮 / Ctrl+C)就都覆盖到了。

**托盘「重启」要等全部清理完才拉新实例**
托盘回调里只置位 `restart_requested` + 走正常退出,新实例由 `main()`
在**所有清理之后**(热键注销 → 窗口销毁 → 模型卸载)用
`DETACHED_PROCESS` 分离拉起。托盘回调里直接拉是错的:那时热键还没让位
(新实例注册必失败)、模型还在显存里(新实例加载可能 OOM)。分离标志让
新进程不挂在旧进程上 —— 旧进程退出后它照常活。

拉起新实例的**命令行必须忠实复刻当初的启动方式**,不能写死
`python -m qwen3_voice`:桌面快捷方式走的是 base 目录的 `pythonw.exe`
+ `scripts/launch.pyw`,而 base 解释器看不见只装在 venv 里的
`qwen3_voice`(实测 `find_spec` 返回 None),照 `-m` 拉起来只会
`ModuleNotFoundError` —— 又因为是 `pythonw`(无控制台)+ `DETACHED`,
那个错根本看不见,新进程**静默闪退**,日志里只剩一句"已拉起新实例"。
所以入口分三种:脚本入口就再跑同一个脚本、`-m` 入口就保持 `-m`、
打包 exe 就再起一个 exe;入口脚本被删/改名时退回 `-m` 并记一条警告。

**面板和胶囊共用一条推送线程**
两条线程并发推同一个 WebView2,事件顺序会乱 —— 胶囊的前端是状态机
(setState → setPreview → setResult 必须按顺序到达)。而且电平采样一次
就能分发给所有窗口,没必要重复采样。

**便携存储**
配置和日志放项目内的 `data/`,不要写 `%APPDATA%` —— 详见仓库根目录
`AGENTS.md`。vibecoding 产物迭代快,系统目录里的旧配置会污染新版本,
而且它不在项目里,`git status` 看不到,删掉项目目录它还在。

**注入要用 SendInput,不要用 keybd_event**
`keybd_event` 是老 API,投递成功与否完全不可知,被 UIPI 拦掉时也照样"成功",
表现出来就是"按了热键没反应"。`SendInput` 会返回**实际投递**的事件数,
据此能知道到底发出去几个;投递不全时只补发抬起事件,绝不重贴(会重复文本)。

**恢复剪贴板的时机**
粘贴是异步的:`SendInput` 只是把 Ctrl+V 塞进系统输入队列,目标应用
什么时候真正去读剪贴板不由我们决定。恢复得太早,目标读到的就是
还没还回去的旧内容 —— 实测表现是"粘贴出来的是上一次的内容"。
所以粘贴后必须等目标消费完才能恢复(这里 1.0s)。

**剪贴板要还,但不能吞掉用户的新内容**
剪贴板只有一份,借了必须还。但无脑还回去会覆盖用户在这期间复制的新内容,
那才是真的丢数据。所以恢复前先比对**剪贴板变更序号**(任何改动都会让它递增)
和当前内容,对不上就**放弃恢复** —— 宁可让用户的新内容留着,也不覆盖它。
最坏情况是"用户原内容没还回去",而不是"用户新内容被吞掉"。

**为什么不用 SendInput + KEYEVENTF_UNICODE 逐字打字**
那种方式不碰剪贴板,看着更"干净",但有两个坑:
打字路径下 `\r` `\n` `\t` 会被 Windows 当成真实按键(回车在聊天软件里
就是"发送消息");部分应用(记事本、WordPad)接受 Unicode 键事件但丢弃字形,
表现是"光标在动但没字"。
参考实现 [OpenType](https://github.com/ct-jyjntc/opentype-public)(AGPL-3.0)
敢用这条路,是因为它有 UI Automation 可以**读回控件内容校验**,知道有没有
部分成功(部分成功时它不重贴,避免重复文本)。我们没有这个校验能力,
盲目走打字路径,一旦部分失败就无法判断该不该重贴 —— 所以保持剪贴板为主路径。

### 调试:录音留存 + 无头回放

「预览不出字」这类问题光看日志不够 —— 日志分不清是**帧没喂进去**、
**全判有声断不出句**、**断句了但识别为空**、还是**认出字了没推给界面**。
所以加了两个基建:

1. **录音留存** —— 每轮录音结束,原始音频自动存成 WAV 到
   `data/recordings/`(文件名带时间戳和时长,只留最近 20 个)。
   不想要就把配置里的 `save_recordings` 关掉。
2. **无头回放** —— 拿留存下来的真实录音复现同一段音频,
   **不加载 UI、不占麦克风**:

```bash
python scripts/replay_preview.py data/recordings/20261029-164630_31s.wav
python scripts/replay_preview.py <wav> --realtime   # 按真实时间推进(复现节奏)
python scripts/replay_preview.py <wav> --verbose    # 逐帧打印 RMS 和静音判定
```

它按录音器的真实块大小喂给**真实的分句引擎**,打印:每个分析帧的 RMS
与静音判定(引擎真正看到的帧)、每次断句的句长/识别文本/耗时、
每次 partial 的累计文本,最后直接给结论 —— 断在哪一环。
